# Схема данных

## `users`

Модель `User` хранит внутренний `id`, уникальный `telegram_id`, имя, телефон,
роль и дату регистрации. Роль хранится для отображения и актуализируется при
работе бота по allowlist из окружения.

## `repair_requests`

Модель `RepairRequest` хранит `id`, обязательный `user_id` с внешним ключом на
`users.id`, описание, статус, приоритет, необязательный диагноз, даты создания и
обновления. При удалении пользователя его заявки удаляются каскадно.

Допустимые статусы, используемые интерфейсом: `new`, `in_progress`, `completed`,
`cancelled`. Значения по умолчанию: `status = new`, `priority = medium`,
`diagnosis = NULL`.

## FSM

Таблица `fsm_storage` создаётся отдельно в той же SQLite-базе. Она хранит
сериализованные состояние и данные диалога по составному Telegram-ключу.

## `repair_request_ai_assessments`

Таблица хранит необязательную предварительную AI-оценку ровно для одной заявки:
Telegram `photo_file_id`, разные тексты для клиента и мастера, перечни деталей и
инструментов, коды прайс-каталога и суммы в копейках. `request_id` уникален и
ссылается на `repair_requests.id` с каскадным удалением. Это новая таблица, поэтому
`create_tables()` создаст её рядом с существующими без изменения старых таблиц.

## `repair_request_staff_edits`

Новая append-only таблица хранит исправления диагноза и клиентской цены,
связанные с заявкой, а также ID сотрудника и снимок его имени на момент правки.
Исходная AI-оценка остаётся неизменной; последняя запись сотрудника показывается
как подтверждённый результат, более ранние записи сохраняют историю. При удалении
заявки её исправления удаляются каскадно. При удалении аккаунта сотрудника ссылка
на него становится пустой, но сохранённое имя автора остаётся в аудите.

Это новая таблица: `create_tables()` создаёт её при запуске рядом с текущими
таблицами. Существующие заявки и AI-оценки не переписываются.

## `urgency_tariffs` и `request_urgencies`

`urgency_tariffs` хранит справочник срочности. При пустой таблице создаются
`ordinary` (0 копеек), `urgent` (50 000 копеек) и `critical` (100 000 копеек).
`request_urgencies` сохраняет для заявки код, название и сумму доплаты на момент
создания. Старые заявки не зависят от последующих изменений тарифа. Обе таблицы
новые и создаются рядом с существующей схемой без изменения старых таблиц.

## Веб-кабинет

`website_accounts` хранит нормализованный email, scrypt-хеш пароля, необязательную
ссылку на `users.id` и адрес по умолчанию. Пароли в открытом виде не сохраняются.
`telegram_link_codes` содержит только SHA-256-хеш одноразового кода, срок
действия и отметку использования; команда `/link` связывает уже зарегистрированный
Telegram ID с веб-аккаунтом. Код истекает через 10 минут и после успешного
использования повторно не принимается.

`request_addresses` хранит необязательный адрес выезда как снимок конкретной
заявки. Его видят только клиент-владелец и сотрудники. `site_texts` содержит
фиксированный список коротких текстов сайта, который может менять администратор.
Все четыре таблицы новые; существующие таблицы для сайта менять не требуется.

Веб-кабинет и бот используют одну SQLAlchemy-сессию и поддерживают SQLite для
разработки или PostgreSQL через `DATABASE_URL`. FSM бота остаётся в SQLite-файле
`DATABASE_PATH`, в том числе после перехода основной базы на PostgreSQL.

## SQLite → PostgreSQL

Команда `python -m repair_bot.scripts.migrate_sqlite_to_postgres` принимает
`SOURCE_SQLITE_PATH` и `TARGET_DATABASE_URL`. Она создаёт онлайн-резервную копию
файла SQLite, требует пустую целевую PostgreSQL-базу, переносит таблицы из
SQLAlchemy metadata и сравнивает количество строк. Неизвестные или непустые
таблицы назначения останавливают перенос. Исходная SQLite-база не изменяется.
FSM-таблица не переносится: она остаётся на том же постоянном файловом томе и
подключается через `DATABASE_PATH`.

## Изменение схемы

`create_tables()` создаёт отсутствующие таблицы, но не меняет существующие.
Перед добавлением, удалением или изменением столбца требуется описать миграцию
или совместимый переход и резервное копирование рабочей базы. Изменение следует
проверять тестами на временной SQLite-базе, а не на `bot_database.db`.

## Подарочные сертификаты — добавочная миграция

`gift_certificates` — новая таблица, исходные таблицы и их колонки не меняются.
Миграция SQLite: `ops/migrations/20261108_gift_certificates.sql` — транзакционная,
повторяемая, содержит только CREATE TABLE/INDEX IF NOT EXISTS. Перед применением
создаётся онлайн-бэкап SQLite; затем схема применяется до перезапуска контейнеров,
чтобы сайт и бот не создавали таблицу одновременно. Для новой БД таблица также
создаётся через metadata. Проверено сохранение старых строк и колонок при
двукратном применении SQL и последующем `create_all()`.

Поля: владелец, уникальная исходная заявка, снимок её номера и итоговой цены,
уникальный случайный код, номинал 100000 копеек, уникальная целевая заявка,
время выдачи и окончательного использования. Связи на удалённые заявки обнуляются,
снимок номера сохраняется; при удалении владельца ORM удаляет его сертификаты.
Резервирование выполняется условным UPDATE и защищается уникальным ограничением
целевой заявки. Выдача идемпотентна по исходной заявке. При отмене целевой заявки
сертификат освобождается, при завершении помечается использованным. Скидка считается
единым helper в сайте и боте, не меняет исходную оценку ИИ и цену в истории правок.


## Добавочные таблицы доступа и переноса (2026-11-09)

Миграция `ops/migrations/20261109_access_and_transfer.sql` содержит только
CREATE TABLE/INDEX IF NOT EXISTS в BEGIN IMMEDIATE; исходные столбцы не меняются.
Перед применением — согласованный онлайн-бэкап и integrity_check, затем создание
таблиц до одновременного старта бота и сайта. Тест проверяет двукратное применение
на старой схеме, сохранность строк пользователей и колонок repair_requests.

- `staff_edit_details`: edit_id (PK/FK), parts/tools, снимок редактируемых полей.
  Старые правки без снимка наследуют последнее известное значение либо оригинал AI.
- `telegram_access_codes`: user_id, HMAC-SHA256 кода, created/expires/used_at.
  Секрет — WEB_SESSION_SECRET (fallback BOT_TOKEN), открытых кодов в БД нет.
- `link_code_rate_limits`: ключ аккаунта или HMAC IP, начало окна и число попыток.
  Лимиты переживают logout и перезапуск, связь и потребление кода атомарны.
- `request_lifecycle`: request_id PK/FK, удаление и имя сотрудника, imported,
  уникальный external_key, provenance JSON, photo_file_id независимо от AI.
- `request_import_batches`: случайный id, администратор, нормализованный архив,
  TTL и used_at; подтверждение условным UPDATE, весь импорт транзакционен.
- `ai_wallets`: telegram_id PK без каскадного FK, free_used, credits. Удаление
  пользователя не даёт повторной бесплатной попытки. Старые AI учитываются при
  первой инициализации. Условные UPDATE предотвращают отрицательный баланс.
- `ai_usages`: request_id PK/FK, инициатор, вид расхода, состояние, счётчик попыток
  и updated_at; reserved не допускает конкурентного вызова для той же заявки.
- `ai_credit_grants`: получатель, имя администратора, количество, сумма копеек,
  основание и уникальная reference формы; выдача/прибавление баланса транзакционны.

Корзина не удаляет сертификаты и правки. Жёсткий CRUD удаления оставлен только
для внутренних сценариев/тестов, веб-интерфейс его не вызывает. Фильтры списков
и счётчиков исключают удалённые записи. Исторические данные импорта не являются
подтверждением права на новый сертификат; проверка стоит в общем issue_for_request.


### Совместимое расширение без новой схемы: фото и установка остатка

`request_lifecycle.photo_file_id` допускает `web:<32 hex>.jpg` для защищённого
файла в общем volume request_photos; старые Telegram ID не преобразуются.
Сохраняется только нормализованный JPEG с серверным случайным именем. Бэкап
хранилища включает снимок SQLite и неизменяемые фото. JSON/CSV экспортируют
ссылки; файлы восстанавливаются отдельно из архива хранилища.

`ai_credit_grants.reason=balance_set`, credits — установленный новый остаток,
amount_kopecks=0; этот вид аудита не означает оплату. Установка обновляет credits
и free_used=True в одной транзакции. Для ещё выполняющихся резервов free/paid
вид расхода становится adjusted_free/adjusted_paid, чтобы последующее отсутствие
провайдера не прибавило попытку поверх установленного числа. reference остаётся
уникальной. Столбцы и таблицы не меняются, SQL-миграция не нужна.
