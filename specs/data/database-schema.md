# Схема данных

## `users`

Модель `User` хранит внутренний `id`, уникальный `telegram_id`, имя, телефон,
роль и дату регистрации. Роль хранится для отображения и актуализируется при
работе бота по allowlist из окружения.

## `repair_requests`

Модель `RepairRequest` хранит `id`, обязательный `user_id` с внешним ключом на
`users.id`, описание, статус, приоритет, необязательный диагноз, даты создания и
обновления. При удалении пользователя его заявки удаляются каскадно.

Допустимые статусы, используемые интерфейсом: `new`, `in_progress`, `completed`,
`cancelled`. Значения по умолчанию: `status = new`, `priority = medium`,
`diagnosis = NULL`.

## FSM

Таблица `fsm_storage` создаётся отдельно в той же SQLite-базе. Она хранит
сериализованные состояние и данные диалога по составному Telegram-ключу.

## `repair_request_ai_assessments`

Таблица хранит необязательную предварительную AI-оценку ровно для одной заявки:
Telegram `photo_file_id`, разные тексты для клиента и мастера, перечни деталей и
инструментов, коды прайс-каталога и суммы в копейках. `request_id` уникален и
ссылается на `repair_requests.id` с каскадным удалением. Это новая таблица, поэтому
`create_tables()` создаст её рядом с существующими без изменения старых таблиц.

## Изменение схемы

`create_tables()` создаёт отсутствующие таблицы, но не меняет существующие.
Перед добавлением, удалением или изменением столбца требуется описать миграцию
или совместимый переход и резервное копирование рабочей базы. Изменение следует
проверять тестами на временной SQLite-базе, а не на `bot_database.db`.
