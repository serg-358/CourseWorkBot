# Repository Guidelines

## Структура проекта и организация модулей

В репозитории находится асинхронный Telegram-бот для заявок на ремонт. Корневой `main.py` — тонкая точка входа; запуск и конфигурация находятся в `repair_bot/bootstrap.py`.

Код приложения размещайте в пакете `repair_bot/`: SQLAlchemy engine и модели — в `database/` (`models/` содержит отдельный файл на модель), CRUD — в `database/crud/`, FSM — в `fsm/` и `states/`, клавиатуры — в `keyboards/`, сервисы — в `services/`. Обработчики разделяйте по сценариям и ролям: регистрация, клиентские заявки, заявки мастера и административные функции; общие проверки выносите в отдельный модуль. Не возвращайте всю логику в один файл. Тесты лежат в `tests/`; каждый тест получает изолированную временную SQLite-базу из `tests/conftest.py`.

## Сборка, тестирование и локальная разработка

Создайте и активируйте виртуальное окружение Python 3.11+, затем установите зависимости для разработки:

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest -q
python main.py
```

`pytest` запускает локальный набор тестов, не затрагивая рабочую базу бота. Для `python main.py` необходим настроенный `.env`. Для запуска в контейнере используйте `docker compose up --build -d`; логи доступны через `docker compose logs -f bot`.

## Стиль кода и соглашения об именовании

Используйте Python с отступом в четыре пробела, типами для публичных функций и `async def` для операций с БД и Aiogram. Для функций, переменных и модулей используйте `snake_case`; для моделей SQLAlchemy и групп состояний — `PascalCase`. Не перегружайте обработчики: проверяйте в них ввод Telegram и права, а переиспользуемые операции с БД размещайте в `repair_bot/database/crud/`.

Ruff настроен на базовые статические проверки; форматирование существующего кода не должно становиться целью несвязанной задачи. Следуйте существующему читаемому стилю, пишите краткие docstring для публичных функций и не включайте в изменения несвязанные рефакторинги.

## Правила тестирования

Используйте `pytest` и `pytest-asyncio`. Имена файлов — `test_*.py`, асинхронных тестов — `async def test_*`. Добавляйте проверки изменённого поведения: ролей, валидации телефона, результатов CRUD, переходов состояний и ошибок. Используйте фикстуру `db_session`, а не рабочий файл базы данных.

## Правила коммитов и pull request

Существующие коммиты используют короткие повелительные формулировки, например `Package repair bot with docs, CRUD tests, and Docker`. Делайте коммиты сфокусированными и описывайте видимое пользователю изменение. В pull request указывайте цель, команду и результат тестов, изменения конфигурации или схемы, а для изменений интерфейса — скриншоты либо примеры сообщений бота.

## Безопасность и конфигурация

Никогда не коммитьте `.env`, токены бота, личные Telegram ID или файлы SQLite. Локально создавайте `.env` на основе `.env.example`. `ADMIN_TELEGRAM_IDS` и `MASTER_TELEGRAM_IDS` задают доверенные начальные роли; связанные с Telegram аккаунты затем может менять только аутентифицированный администратор сайта. Bootstrap-роли из `.env` нельзя понизить через сайт. Проверяйте роль по базе при каждом запросе и не доверяйте username, hidden-полям или callback-данным. Для изменений схемы требуется стратегия миграций: `create_tables()` не обновляет существующие таблицы.

## Рабочий процесс Codex и спецификации

Краткая передача текущего состояния и незавершённых задач: `PROJECT_CONTEXT.md`.

Перед изменением сценария бота прочитайте `specs/features/repair-requests.md`; перед изменением моделей или таблиц — `specs/data/database-schema.md`. Используйте навыки из `.agents/skills/`, когда их описание соответствует задаче. Спецификации описывают только проверенное текущее поведение: AI-диагностику нельзя называть реализованной, пока не появятся код и тесты.

Перед планированием VPS-развёртывания, миграции базы данных, изменения модели
данных, AI-интеграции или добавления модуля инвентаря обязательно используйте
skill `grilling`, даже если пользователь не написал эту команду явно. Сначала
уточните связанные решения и получите подтверждение общего плана; затем
переходите к реализации. Не используйте `grilling` для обычных небольших
исправлений.

Для изменений кода выполните `python -m ruff check .` и `python -m pytest -q`. Перед коммитом установленный `pre-commit` выполняет те же проверки. В итоговом сообщении укажите, какие проверки запускались и что осталось непроверенным.

## Цикл завершения задачи

После реализации агент обязан самостоятельно пройти цикл «проверка → диагностика →
минимальное исправление → повторная проверка». Не завершайте задачу при известной
ошибке Ruff, pytest или pre-commit и не обходите проверку отключением теста или
правила линтера. Продолжайте цикл, пока все относящиеся к задаче проверки не
станут зелёными.

Для одной и той же причины сбоя разрешено не более трёх циклов исправления.
После третьей неудачи остановитесь и сообщите пользователю проверку, ключевую
ошибку, уже предпринятые исправления и требуемое следующее решение. Не начинайте
новый цикл с тем же сбоем без новых данных или указаний пользователя.

Остановитесь и запросите пользователя только при внешнем блокере: неясном
требовании, необходимом секрете/API-ключе, доступе к VPS, необратимой операции,
решении о миграции или ошибке, не связанной с текущей задачей. Не исправляйте
несвязанные изменения пользователя без отдельного разрешения.

## Инструменты Codex

Проектный MCP `openaiDeveloperDocs` предназначен только для вопросов об OpenAI API, ChatGPT, Codex и связанных плагинах. Не используйте его как источник правил предметной области бота и не передавайте ему секреты, содержимое `.env` или данные пользователей.
