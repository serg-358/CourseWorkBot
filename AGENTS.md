# Repository Guidelines

## Структура проекта и организация модулей

В репозитории находится асинхронный Telegram-бот для заявок на ремонт. `main.py` загружает конфигурацию и запускает Aiogram polling. Модели SQLAlchemy и настройка базы находятся в `models.py` и `database.py`; постоянное хранилище FSM реализовано в `fsm_storage.py`.

Обработчики пользовательских сценариев размещайте в `handlers/`, а функции доступа к данным — в `crud/` (`users.py` и `requests.py`). Клавиатуры находятся в `keyboards.py`, состояния диалогов — в `states.py`. Тесты лежат в `tests/`; каждый тест получает изолированную временную SQLite-базу из `tests/conftest.py`.

## Сборка, тестирование и локальная разработка

Создайте и активируйте виртуальное окружение Python 3.11+, затем установите зависимости для разработки:

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest -q
python main.py
```

`pytest` запускает локальный набор тестов, не затрагивая рабочую базу бота. Для `python main.py` необходим настроенный `.env`. Для запуска в контейнере используйте `docker compose up --build -d`; логи доступны через `docker compose logs -f bot`.

## Стиль кода и соглашения об именовании

Используйте Python с отступом в четыре пробела, типами для публичных функций и `async def` для операций с БД и Aiogram. Для функций, переменных и модулей используйте `snake_case`; для моделей SQLAlchemy и групп состояний — `PascalCase`. Не перегружайте обработчики: проверяйте в них ввод Telegram и права, а переиспользуемые операции с БД размещайте в `crud/`.

Ruff настроен на базовые статические проверки; форматирование существующего кода не должно становиться целью несвязанной задачи. Следуйте существующему читаемому стилю, пишите краткие docstring для публичных функций и не включайте в изменения несвязанные рефакторинги.

## Правила тестирования

Используйте `pytest` и `pytest-asyncio`. Имена файлов — `test_*.py`, асинхронных тестов — `async def test_*`. Добавляйте проверки изменённого поведения: ролей, валидации телефона, результатов CRUD, переходов состояний и ошибок. Используйте фикстуру `db_session`, а не рабочий файл базы данных.

## Правила коммитов и pull request

Существующие коммиты используют короткие повелительные формулировки, например `Package repair bot with docs, CRUD tests, and Docker`. Делайте коммиты сфокусированными и описывайте видимое пользователю изменение. В pull request указывайте цель, команду и результат тестов, изменения конфигурации или схемы, а для изменений интерфейса — скриншоты либо примеры сообщений бота.

## Безопасность и конфигурация

Никогда не коммитьте `.env`, токены бота, личные Telegram ID или файлы SQLite. Локально создавайте `.env` на основе `.env.example`. Роли должны определяться через `ADMIN_TELEGRAM_IDS` и `MASTER_TELEGRAM_IDS`; не доверяйте username и callback-данным без проверки. Для изменений схемы требуется стратегия миграций: `create_tables()` не обновляет существующие базы.

## Рабочий процесс Codex и спецификации

Перед изменением сценария бота прочитайте `specs/features/repair-requests.md`; перед изменением моделей или таблиц — `specs/data/database-schema.md`. Используйте навыки из `.agents/skills/`, когда их описание соответствует задаче. Спецификации описывают только проверенное текущее поведение: AI-диагностику нельзя называть реализованной, пока не появятся код и тесты.

Перед планированием VPS-развёртывания, миграции базы данных, изменения модели
данных, AI-интеграции или добавления модуля инвентаря обязательно используйте
skill `grilling`, даже если пользователь не написал эту команду явно. Сначала
уточните связанные решения и получите подтверждение общего плана; затем
переходите к реализации. Не используйте `grilling` для обычных небольших
исправлений.

Для изменений кода выполните `python -m ruff check .` и `python -m pytest -q`. Перед коммитом установленный `pre-commit` выполняет те же проверки. В итоговом сообщении укажите, какие проверки запускались и что осталось непроверенным.

## Инструменты Codex

Проектный MCP `openaiDeveloperDocs` предназначен только для вопросов об OpenAI API, ChatGPT, Codex и связанных плагинах. Не используйте его как источник правил предметной области бота и не передавайте ему секреты, содержимое `.env` или данные пользователей.
